---
name: Yahoo Fantasy connection
description: Distinguish Fantasy OAuth hosts and permissions; do not infer a scope or pop-up error from a pre-sign-in setup failure.
---

For Fantasy Sports access, enter `fantasysports.yahooapis.com` as the Yahoo connector's API Domain, with no scheme or trailing slash. The `api.login.yahoo.com` example shown in the connection form serves the identity API, not fantasy leagues. However, `api.login.yahoo.com` is also the correct OAuth host: authorization uses `/oauth2/request_auth`, and server-side token exchange uses `/oauth2/get_token`. Do not confuse the resource API host with the authorization host.

The correct API Domain does not establish that Fantasy permissions were granted. Connector documentation lists `openid` as the default, while Fantasy reads require `fspt-r`. Do not diagnose a generic “Unauthorized” as a missing scope without knowing where it occurred. An error inside Replit's API Domain setup before Yahoo sign-in is not evidence of a rejected Yahoo password or a missing grant on an already-authorized connection. A subsequent OAuth pop-up failure can be secondary to the setup error; it does not by itself prove a browser pop-up blocker caused the failure. Refreshing, signing out/in, allowing pop-ups and the account-level Integrations route also failed to resolve that setup failure; its root cause remains unverified.

**Why:** Correct-host setup continued to fail before Yahoo sign-in, and a subsequent pop-up failure message still did not establish the root cause. Distinguishing the stages prevents unsupported password, scope, or browser diagnoses.

**How to apply:** When helping configure Yahoo, use the Fantasy Sports host and ensure the read grant includes `fspt-r`. Re-read current integration notes before changing setup. Guide the setup, Yahoo sign-in, consent, and return-to-Replit stages distinctly. For a pre-sign-in setup failure, distinguish session or workspace permission issues from connector configuration problems; do not keep reopening the identical failed flow or promise a scope change will fix it. After authorization, verify an authenticated NBA-league read. League/draft endpoints being exposed does not establish that picks update during live drafts; test freshness before promising automatic sync.

Yahoo requires the OAuth application's registration to enable private Fantasy Sports data access; an API Domain field does not configure the application credentials or permissions. With a managed connector, the connector owner supplies this registration, not each person signing in.

**Why:** Yahoo's Fantasy documentation explicitly requires an application registration with Fantasy Read access, while the connector exposes a resource-domain choice that can appear to be the entire setup.

**How to apply:** Check the actual OAuth configuration or a sanitized failure code before claiming a specific root cause. Replit documents a separate account-level sign-in route at Workspace home → Integrations → All integrations, which can distinguish a chat-popup failure from a general connector failure. Replit's documented bring-your-own OAuth configuration for existing connectors is Enterprise-only; do not promise a personal Yahoo app can be pasted into the default API Domain dialog. Recheck current platform documentation before recommending that route.

Sources: [Yahoo Fantasy setup](https://sports.yahoo.com/developer/docs/), [Yahoo authorization-code flow](https://developer.yahoo.com/oauth2/guide/flows_authcode/), [Replit connector configuration](https://docs.replit.com/features/integrations/overview#configuring-oauth-app-with-replit), [Replit integration management](https://docs.replit.com/replitai/managing-connectors).

Yahoo's current [Fantasy developer portal](https://sports.yahoo.com/developer) describes submitting an [access application](https://sports.yahoo.com/developer/access/), review and approval, including for personal or single-league use. Possessing a Yahoo client ID and secret alone does not establish Fantasy API read permission. The current access form states that access is read-only and write access is unavailable, despite older setup documentation still describing a Read/Write choice.

**Why:** The current portal adds an access-review requirement and access restrictions that older application-registration instructions may not reflect. This does not establish the cause of a generic authorization error or the earlier managed-connector failure.

**How to apply:** Recheck the portal, application approval and actual grants when enabling access. Prefer the current access policy over older permission-picker instructions. Verify an authenticated Fantasy read before treating registration as complete. The documented `draftresults` resource is not itself a guarantee of live-draft latency; measure observed pick delay before presenting a live-sync claim.

For app-owned OAuth, the user reports that Fantasy Sports Read access is enabled or approved. Treat that as reported registration status, not proof of a successful authenticated league read. Successful OAuth and Fantasy API authorization are separate: even after sign-in completes, an authenticated Fantasy request can return HTTP 403.

**Why:** The user confirmed access while diagnosing a generic pre-sign-in error; after callback matching was corrected, sign-in succeeded but the Fantasy read was refused. Neither error establishes that a permission checkbox was missed. Current [community reports](https://github.com/uberfastman/yfpy/issues/84) describe post-OAuth 403s even for approved applications; their provisioning explanations are reports, not a confirmed cause for this app.

**How to apply:** Check callback matching and whether the credential is the Client ID/Consumer Key rather than the App ID before asking the user to repeat the access application. Compare the registered callback's full path, not just its origin: doubled path slashes are significant and must not be silently treated as equivalent. For post-OAuth denials, use a safely classified provider response to distinguish app authorization, additional authorization and an expired token. Check that any approval and completion steps apply to the same application; do not repeatedly reconnect or change credentials without evidence. A [September 14, 2026 community report](https://github.com/uberfastman/yfpy/issues/84#issuecomment-5669815953) describes a Developer Application Confirmation Form in the agreement-completion email, requesting the Client ID/Consumer Key and App ID even when Fantasy permissions are absent from the registration UI. Treat this as a reported step to check in the user's own Yahoo correspondence, not a universal requirement or a verified fix. The current official access form labels its existing-registration field Client ID; do not substitute App ID based on older community wording. Recheck approval if the Yahoo application changes; do not claim real account access is verified until a league read succeeds.
